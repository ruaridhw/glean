# Recipe enrichment is a pipeline of declarative enrichers behind one runner

Everything the planner needs to know about a recipe beyond its own text — whether it breaks a dietary flag, its main protein, its active time — costs a decision-model call. Enrichment is therefore a first-class backend package, `recipes/enrichment/` (spec 6.1, F2), not a script per derived fact:

- **Enrichers declare questions.** An enricher is one family of questions ("dietary", "attributes", "active time"). Each question carries the wording handed to the decision model, its criteria, its confidence bar and the rule that turns a raw answer into a stored value. An enricher never asks, batches or stores anything itself.
- **The runner asks once per recipe.** For each recipe it collects every question that is missing or stale *across all enrichers* and sends them in one `DecisionClient.decide` request. A recipe with nothing to ask makes no request.
- **Every answer is its own item,** keyed `(recipe, question, criteria hash)` in #162's store. A question is **stale** when its criteria hash changed (the wording was edited), when the recipe's content hash changed (title or ingredients were edited), or when the answer came from another model than the pinned one. So editing one question's wording re-asks only that question, still as one request per recipe, and stored answers survive a deploy that changed nothing.
- **Confidence bars decide what a question accepts.** No answer is accepted because it is the top option. Each question states a threshold *and which side of it is safe*: a dietary question is safe at a low probability, so its 0.3 is an exclusion threshold applied when planning reads the answer (ADR 0011); an attribute question is safe at a high probability, so 0.8 is the probability a stored option needs before it is read as a label rather than as `unsure`. The bar is declared where the question is, so the runner, the coverage report and a reviewer read one fact. An attribute's bar is tunable per attribute from a labelled sample and may never be declared below 0.7 (G1); `attribute_bar` refuses one that is.
- **An answer stores what the model said, and the bar is a policy over it.** A `noul` answer is its probability. A `choice` or `score` answer stores the option the model chose — a label, an active-time bucket — and the probability that chose it, whatever the question's bar is. The bar is applied when the answer is **read**, so an attribute under its bar reads as `unsure`: a real answer that stops the recipe being re-asked and earns no variety credit and no penalty. That is what makes retuning a bar free — raising one turns the labels it now rejects into `unsure`, lowering one recovers labels stored under the old bar, and neither re-asks the corpus — and it is the same shape dietary has always had. A dietary answer's item and JSONL line are byte-for-byte what they were before, so nothing already computed is invalidated.
- **It is a producer, run by the owner,** after a corpus import, a question rewording or a model bump — never inside a request (spec 7). `make enrich-corpus` and `scripts/enrich_corpus.py` are the entry points; the script refuses a prod table or bucket without `--i-am-the-owner`, needs the decision API key in the environment, and exits non-zero unless every recipe has a current answer to every question, which is the deploy gate. A scheduled run is parked (spec 9).

## Considered options

- **A script per derived fact** (what the dietary producer was). Rejected: each new fact re-implements staleness, batching, checkpointing and reporting, and every one of them spends its own model request per recipe.
- **One decision request for a batch of recipes.** Rejected: the request carries one `state` (one recipe), and a thousand-recipe batch would be one failure away from losing everything.
- **Rebuilding the projection per recipe.** Rejected: the runner writes answers in checkpoints and rebuilds the projection once at the end, because a per-recipe rebuild is one S3 write per paid call.
- **Storing a `unsure`/label value on the answer item at F2's time.** Deferred to V5, which then added it (`RecipeAnswer.value`) with the questions that need it: dietary's answer stays the probability alone, and an attribute's answer is the value it accepted.

## Consequences

- **The stored answers are the checkpoint.** A run that stops partway has written what it got, so the next run asks only what is left; no progress file can drift from the store.
- **V5's attributes needed a stored value, and V5 added it.** The question union (`noul`, `choice`, `score`), the acceptance hook and the per-recipe batching carried over unchanged; what changed is the answer item (`value` = the option the model chose, with `probability` = that option's probability) and the read-time application of the bar, which turns an option under it into `unsure` instead of discarding it. `None` still means "nothing stored, ask again", which is a different thing from `unsure`.
- **Adding an enricher therefore costs coverage work and, for a non-probability answer, that answer-shape change.** Its questions join the same request and the same coverage report (current / stale / missing / failed / unsure, plus the count of recipes that state a prep time); it is not a declaration alone. V5's three families (`dietary`, `attributes`, `active-time`) share one per-recipe request, and the coverage report counts how many current answers are `unsure` beside how many are labelled.
- **A projection entry carries the derived attributes.** Every recipe's attributes are recomputed from its current answers whenever the projection is rebuilt or an answer is saved (`attributes_from_answers`), so the entry is a cache of the answers and an edited recipe voids the attributes asked about its old body. Reading them needs no extra item: planning reads the entry, and the filter's time cap compares the active-time bucket's upper bound, falling back to total time when nothing is known.
- **The corpus is never trusted to be complete.** With no ingredient rules to fall back on, a recipe missing a current dietary answer is excluded under that flag; running enrichment is part of shipping a corpus change.
