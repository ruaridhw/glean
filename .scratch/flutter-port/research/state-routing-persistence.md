# Flutter Ecosystem Research: Routing, State Management, Local Persistence

**Purpose:** Input to a human decision about Glean's Flutter rewrite (big-bang replacement of the current Expo/React Native app — no coexistence, no legacy-schema migration constraint). This document is a sourced comparison of options across three layers. It is **not a recommendation** — a human will decide the stack later based on these findings plus other project context.

All facts below are cited to primary sources (pub.dev package pages, official docs, GitHub repo API data) fetched on **2026-07-25**. Numbers like stars/likes/downloads will drift over time; re-check before final decision if this document is read much later.

---

## Layer 1: Routing

Glean's UI is a bottom-tab layout where each tab (meals, pantry, plan, shop, settings) keeps an **independent back-stack** that survives switching tabs — the Flutter equivalent of Expo Router's tab layout / React Navigation nested stacks.

| Option | Key strengths | Key weaknesses / gaps | Maintenance / adoption signal |
|---|---|---|---|
| **go_router** | First-party, Flutter-team-published. `StatefulShellRoute` (`StatefulShellRoute.indexedStack`) creates **separate `Navigator`s per branch/tab**, each with its own history, restored on `goBranch()` — a direct match for Glean's per-tab stack requirement ([API docs](https://pub.dev/documentation/go_router/latest/go_router/StatefulShellRoute-class.html)). URL-based deep linking built in. Optional type-safe params via companion `go_router_builder` code-gen package. Official Flutter docs explicitly recommend it: *"Flutter applications with advanced navigation and routing requirements ... should use a routing package such as go_router"* ([docs.flutter.dev/ui/navigation](https://docs.flutter.dev/ui/navigation)). | `StatefulShellRoute` requires supplying a `navigatorContainerBuilder` for custom layouts/animations — some boilerplate beyond the `indexedStack` default. Type safety is opt-in (separate package), not built into the core API. | Published by publisher **flutter.dev** (verified). v17.3.0, published 52 days before 2026-07-25 ([pub.dev/packages/go_router](https://pub.dev/packages/go_router)). 150 pub points, 5,750 likes, 3.52M weekly downloads. Hosted in the `flutter/packages` monorepo: 5,268 GitHub stars, 109 open issues, last commit 2026-07-24 ([GitHub API](https://github.com/flutter/packages)). `go_router_builder` v4.4.0, published 3 days before 2026-07-25, also flutter.dev-published ([pub.dev/packages/go_router_builder](https://pub.dev/packages/go_router_builder)). |
| **auto_route** | Heavier code-gen model: `@RoutePage()`/`@AutoRouterConfig()` generate typed route classes, eliminating stringly-typed params entirely (stronger default type-safety than go_router without an add-on). `AutoTabsRouter` is purpose-built for state-preserving tab navigation with `PageView`/`TabBar` support — arguably a more direct "tabs with independent stacks" abstraction than go_router's shell-route construct. Built-in route guards. | Not first-party; single-maintainer-adjacent project (Codeness.ly publisher) rather than Flutter-org-backed. Requires `build_runner` codegen step for all routes (heavier build pipeline than go_router's optional codegen). | Publisher **Codeness.ly** (verified). v11.1.0, published 7 months before 2026-07-25 ([pub.dev/packages/auto_route](https://pub.dev/packages/auto_route)). 150 pub points, 3.4k likes, 354k weekly downloads — an order of magnitude fewer downloads than go_router. GitHub repo `Milad-Akarie/auto_route_library`: 1,752 stars, **260 open issues**, last push 2026-06-13 ([GitHub API](https://github.com/Milad-Akarie/auto_route_library)) — notably higher open-issue count and older last-push than go_router. |
| **Raw Navigator 2.0 / Router API** | No third-party dependency; full control; no codegen step; no risk of a package going unmaintained. | Nested independent-stack-per-tab (Glean's core requirement) must be hand-built via manual `IndexedStack` + one `Navigator` per branch, each wired to its own `NavigatorState`/`Navigator.pages` — this is exactly the pattern go_router's `StatefulShellRoute` and auto_route's `AutoTabsRouter` implement *for* you. Deep linking, route-param typing, and browser/URL sync are all manual. Historically considered verbose/complex even by Flutter's own team, which is why go_router was created as an official abstraction over it. | N/A (part of the Flutter SDK itself — no separate pub.dev/GitHub maintenance signal). Effort is the cost, not a maintenance risk. |

**Sources:** [go_router on pub.dev](https://pub.dev/packages/go_router) · [go_router StatefulShellRoute API](https://pub.dev/documentation/go_router/latest/go_router/StatefulShellRoute-class.html) · [go_router_builder on pub.dev](https://pub.dev/packages/go_router_builder) · [flutter/packages GitHub](https://github.com/flutter/packages) · [Flutter official navigation docs](https://docs.flutter.dev/ui/navigation) · [auto_route on pub.dev](https://pub.dev/packages/auto_route) · [auto_route_library GitHub](https://github.com/Milad-Akarie/auto_route_library)

**Leaning (not a decision):** go_router is the Flutter-team-endorsed default, has by far the larger download/star base, and `StatefulShellRoute.indexedStack` maps almost 1:1 onto Glean's "independent stack per tab" requirement with relatively little code. auto_route's `AutoTabsRouter` and stronger default type-safety are real advantages, but its lower adoption, higher relative open-issue count, and older last-push are worth weighing against go_router's first-party backing. Raw Navigator 2.0 buys independence from any package but reproduces functionality both libraries give for free — worth considering only if the team wants zero routing-package risk and is willing to own that complexity.

## Layer 2: State Management

Core question per option: **how do you cache/invalidate server-state queries the way TanStack Query does** (async fetch with caching, background refetch, invalidate-on-mutation, staleness)?

| Option | Server-state caching story | Key weaknesses / gaps | Maintenance / adoption signal |
|---|---|---|---|
| **Riverpod** | Built-in primitives cover most of TanStack Query's surface without an extra package: `FutureProvider`/`AsyncNotifier` wrap async work in `AsyncData`/`AsyncLoading`/`AsyncError`; `ref.watch` creates automatic dependency-based refetching; **`family`** parameterizes cached state per argument (e.g. per recipe id) — "think of it as a Map" ([riverpod.dev/docs/concepts2/family](https://riverpod.dev/docs/concepts2/family)); **`autoDispose`** evicts unused cache entries once listener count hits zero, with `ref.keepAlive()` for selective retention (e.g. keep on success, drop on failure) ([riverpod.dev/docs/concepts2/auto_dispose](https://riverpod.dev/docs/concepts2/auto_dispose)); **`ref.invalidate(provider)`** (or `ref.invalidateSelf()`) forces a refetch, invalidating either all family-parameter combinations or one specific combination — the direct analogue of TanStack's `invalidateQueries`. For an even closer TanStack-Query clone there's the community package **fquery** (`useQuery`/`useMutation` hooks, stale time, GC, dependent queries, optimistic mutations) built on `flutter_hooks`, v3.1.0 published 29 days before 2026-07-25, 155 pub points, 88 likes, **unverified publisher** ([pub.dev/packages/fquery](https://pub.dev/packages/fquery)) — much smaller adoption than riverpod itself. | The built-in caching model requires understanding several composable modifiers (`family` + `autoDispose` + `keepAlive`) rather than one cohesive "query" API; fquery narrows that gap but is a small, unverified-publisher package, a materially different risk profile than riverpod core. | Publisher **dash-overflow.net** (verified, i.e. Remi Rousselet). v3.3.2, published 44 days before 2026-07-25, 160 pub points, 4,010 likes, 2.61M downloads ([pub.dev/packages/riverpod](https://pub.dev/packages/riverpod)). GitHub `rrousselGit/riverpod`: 7,344 stars, 155 open issues, last push 2026-07-21 ([GitHub API](https://github.com/rrousselGit/riverpod)). |
| **Bloc / Cubit** | No built-in query cache. The pattern is "fetch in an event handler, emit a new state" — caching/dedup/staleness must be hand-rolled (e.g. a repository layer with its own in-memory cache + manual invalidation calls). The ecosystem's answer to *concurrency* (not caching) is **bloc_concurrency**, which offers `concurrent`/`sequential`/`droppable`/`restartable` event transformers to prevent race conditions on rapid-fire events ([pub.dev/packages/bloc_concurrency](https://pub.dev/packages/bloc_concurrency)) — this solves overlapping-request ordering, not cache invalidation. **hydrated_bloc** persists/restores bloc state (via Hive) across app restarts ([pub.dev/packages/hydrated_bloc](https://pub.dev/packages/hydrated_bloc)) — persistence, not server-state cache/staleness. No dedicated TanStack-Query-equivalent package with comparable adoption was found for Bloc. | Heaviest hand-rolling burden of the three real contenders for the specific "cache + invalidate + stale + refetch" requirement Glean needs; boilerplate-heavy (separate event/state classes) relative to Riverpod. | flutter_bloc is a **Flutter Favorite**, publisher **bloclibrary.dev** (verified). v9.1.1, published 14 months before 2026-07-25 (older release cadence than riverpod/provider), 160 pub points, 8,050 likes, 1.76M downloads ([pub.dev/packages/flutter_bloc](https://pub.dev/packages/flutter_bloc)). GitHub `felangel/bloc`: 12,477 stars (highest of any package researched here), 78 open issues, last push 2026-07-24 ([GitHub API](https://github.com/felangel/bloc)). bloc_concurrency v0.3.0 published 18 months before 2026-07-25, 586 likes ([pub.dev/packages/bloc_concurrency](https://pub.dev/packages/bloc_concurrency)); hydrated_bloc v11.0.0 published 4 months before 2026-07-25, 971 likes ([pub.dev/packages/hydrated_bloc](https://pub.dev/packages/hydrated_bloc)). |
| **Provider** | Minimal built-in async tooling — it's an ergonomic wrapper around `InheritedWidget` ("a wrapper around InheritedWidget to make them easier to use and more reusable," per its own pub.dev description ([pub.dev/packages/provider](https://pub.dev/packages/provider))) plus `ChangeNotifier` for mutable state and dependency injection through the widget tree. There is no cache/staleness/invalidation primitive at all — a `FutureProvider` exists for one-shot async values but has none of Riverpod's `family`/`autoDispose`/`invalidate` machinery. Any TanStack-Query-like behavior would be entirely hand-rolled on top of a `ChangeNotifier` repository. | Simplest mental model of the three, but that simplicity is exactly the gap: no query-cache abstraction, no built-in staleness/refetch, no family-style per-parameter caching. The same author (Remi Rousselet / dash-overflow.net) built Riverpod specifically to address Provider's limitations. | Publisher **dash-overflow.net** (verified). v6.1.5+1, published 11 months before 2026-07-25, 150 pub points, **11k likes** (highest raw like-count of the three, reflecting historical dominance before Riverpod), 1.12M downloads ([pub.dev/packages/provider](https://pub.dev/packages/provider)). GitHub `rrousselGit/provider`: 5,259 stars, 38 open issues (lowest of the three — consistent with a package in maintenance mode, not active feature development), last push 2026-03-10, the **oldest** last-push of the three state-management options ([GitHub API](https://github.com/rrousselGit/provider)). |
| **Plain InheritedWidget + ChangeNotifier** | Zero dependencies, full control, nothing to go unmaintained. | No caching, no invalidation, no staleness tracking, no devtools integration — everything Provider/Riverpod give for free must be built by hand, including the InheritedWidget boilerplate Provider exists specifically to eliminate. | N/A — part of the Flutter SDK; no package-level maintenance signal. |

**Sources:** [riverpod on pub.dev](https://pub.dev/packages/riverpod) · [riverpod GitHub](https://github.com/rrousselGit/riverpod) · [Riverpod autoDispose docs](https://riverpod.dev/docs/concepts2/auto_dispose) · [Riverpod family docs](https://riverpod.dev/docs/concepts2/family) · [fquery on pub.dev](https://pub.dev/packages/fquery) · [flutter_bloc on pub.dev](https://pub.dev/packages/flutter_bloc) · [bloc GitHub](https://github.com/felangel/bloc) · [bloc_concurrency on pub.dev](https://pub.dev/packages/bloc_concurrency) · [hydrated_bloc on pub.dev](https://pub.dev/packages/hydrated_bloc) · [provider on pub.dev](https://pub.dev/packages/provider) · [provider GitHub](https://github.com/rrousselGit/provider)

**Leaning (not a decision):** Riverpod is the only option among the four with first-party primitives (`family` + `autoDispose` + `ref.invalidate`) that map directly onto TanStack Query's cache/invalidate/stale model, which is the exact capability Glean needs to replace its current TanStack Query layer — but that mapping is spread across several composable modifiers rather than one unified API, and the closer fquery analogue is small and unverified. Bloc/Cubit has the largest GitHub star count and Flutter-Favorite status but offers nothing built-in for query caching, pushing that complexity into hand-rolled repository code. Provider and raw InheritedWidget+ChangeNotifier are both weaker fits specifically for the server-state-cache requirement, though Provider remains a reasonable choice if the team values its comparative simplicity over query-cache ergonomics.

## Layer 3: Local Persistence

Real local relational store (not just a cache) for pantry items, meal plans, shopping lists — the Flutter analogue of the current Drizzle-over-expo-sqlite setup.

| Option | Schema migrations | Type-safety / query shape | Maintenance / adoption signal |
|---|---|---|---|
| **drift** | Purpose-built migration framework: bump `schemaVersion`, then either hand-write a `MigrationStrategy` (`onCreate`/`onUpgrade`/`beforeOpen` callbacks, `Migrator.createTable`/`addColumn`/`dropTable`) or use the `make-migrations` CLI tool, which **generates step-by-step migration code and a matching migration test file** automatically ([drift.dev migrations docs](https://drift.simonbinder.eu/docs/advanced-features/migrations/)) — the strongest migration tooling of the four options researched. | SQL-like: define tables/queries in Dart or `.drift` SQL files; codegen produces fully typed row classes and query methods, catching column/type errors at compile time. Supports joins, filters, window functions, and **auto-updating reactive streams** across multiple tables ([pub.dev/packages/drift](https://pub.dev/packages/drift)) — closest conceptual match to Drizzle's typed-SQL-builder model. | Flutter Favorite, publisher **simonbinder.eu** (verified). v2.34.2, published **10 days before 2026-07-25** — most recently updated of the four persistence options ([pub.dev/packages/drift](https://pub.dev/packages/drift)). 160 pub points, 2.44k likes, 1.04M downloads. GitHub `simolus3/drift`: 3,249 stars, 210 open issues, last push 2026-07-23 ([GitHub API](https://github.com/simolus3/drift)). Backed by sponsors including Stream and PowerSync per its own pub.dev listing. |
| **sqflite** | No migration framework at all — the package only exposes a raw `onCreate`/`onUpgrade` callback pair at database-open time; all migration logic (detecting version, writing/ordering `ALTER TABLE` statements) is fully manual, comparable to writing raw SQL migrations by hand. | Raw SQL strings via `execute`/`query`/`insert`/`update`/`delete` helpers — no compile-time type-checking of queries or schema; results are `Map<String, Object?>` that must be manually mapped to model classes. Explicitly documents that **concurrent read/write transactions are not supported** — all calls are synchronized ([pub.dev/packages/sqflite](https://pub.dev/packages/sqflite)). | Publisher **tekartik.com** (verified). v2.4.3, published 52 days before 2026-07-25, 160 pub points, 5.55k likes, 2.56M weekly downloads (highest raw download count of the four, likely reflecting its role as a low-level dependency of higher-level packages like drift). GitHub `tekartik/sqflite`: 3,017 stars, only 5 open issues, last push 2026-07-22 ([GitHub API](https://github.com/tekartik/sqflite)). |
| **isar** | Schema is declared via `@Collection` annotations + codegen; migrations are largely implicit/schema-diff based rather than an explicit step-by-step API — but this is now moot given maintenance status below. | NoSQL-object-store shape: typed Dart objects with generated `IsarCollection` accessors; queries are a fluent typed query builder (`.filter().fieldEqualTo(...)`), not SQL. Supports full-text search and is fully async. | **Maintenance status is a real concern, confirmed via primary sources.** The canonical `isar/isar` GitHub repo's latest **stable** release (3.1.0+1) was published **3 years** before 2026-07-25, with only a stalled `4.0.0-dev.14` prerelease beyond it ([pub.dev/packages/isar](https://pub.dev/packages/isar)); its last commit was 2025-06-14, over a year stale, though the repo is not formally archived ([GitHub API](https://github.com/isar/isar)). The community picked up maintenance: **isar_community** (publisher isar-community.dev, verified) is at v3.3.2, published 4 months before 2026-07-25, but its own pub.dev description scopes the fork narrowly to *"bug fixes and small updates for version 3"* ([pub.dev/packages/isar_community](https://pub.dev/packages/isar_community)) — i.e., stabilization, not new feature development. On GitHub, the org's fork repo was **renamed/moved**: `isar-community/isar` is archived (last push 2025-08-18) and superseded by `isar-community/isar-community`, which is active (last push 2026-07-03, 189 stars, 39 open issues) ([GitHub API queries against isar-community org](https://github.com/isar-community)). Net: the original package is effectively unmaintained past v3; the community fork keeps v3 alive for bug fixes only, with no clear path to a maintained v4. |
| **objectbox** | **Semi-automatic**: ObjectBox tracks a JSON "meta model" file (checked into version control) and handles field/entity add/remove automatically. Renames require explicit `@Uid` annotation + a two-step build (first build fails and reports the UID to apply, second build completes the rename) — otherwise a rename is silently treated as delete+create. Concurrent-branch conflicts require manually editing the JSON file's `lastEntityId`/`lastPropertyId` ([docs.objectbox.io](https://docs.objectbox.io/advanced/meta-model-ids-and-uids)). Less ergonomic than drift for renames; more automatic than sqflite for additions/removals. | NoSQL-object-store shape like isar: `@Entity()`-annotated Dart classes, codegen produces typed box/query APIs with built-in relations. Vendor claims "10X faster than SQLite" on its own benchmarks ([pub.dev/packages/objectbox](https://pub.dev/packages/objectbox)) — a vendor claim, not independently verified here. | Publisher **ObjectBox.io** (verified). v5.3.2, published 2 months before 2026-07-25, 160 pub points, 1.57k likes, 143k weekly downloads (smallest download count of the four) ([pub.dev/packages/objectbox](https://pub.dev/packages/objectbox)). GitHub `objectbox/objectbox-dart`: 1,233 stars, 78 open issues, last push 2026-07-20 — actively maintained, commercially backed (company also sells a "Data Sync" product). |

**Sources:** [drift on pub.dev](https://pub.dev/packages/drift) · [drift GitHub](https://github.com/simolus3/drift) · [drift migrations docs](https://drift.simonbinder.eu/docs/advanced-features/migrations/) · [sqflite on pub.dev](https://pub.dev/packages/sqflite) · [sqflite GitHub](https://github.com/tekartik/sqflite) · [isar on pub.dev](https://pub.dev/packages/isar) · [isar GitHub](https://github.com/isar/isar) · [isar_community on pub.dev](https://pub.dev/packages/isar_community) · [isar-community GitHub org](https://github.com/isar-community) · [objectbox on pub.dev](https://pub.dev/packages/objectbox) · [objectbox-dart GitHub](https://github.com/objectbox/objectbox-dart) · [ObjectBox schema-change docs](https://docs.objectbox.io/advanced/meta-model-ids-and-uids)

**Leaning (not a decision):** drift is the most actively developed of the four (published 10 days before this research, 160 pub points, Flutter Favorite) and has the most mature migration tooling (`make-migrations` codegen + generated migration tests) plus a SQL-like typed-query shape closest to the team's existing Drizzle mental model. isar's maintenance status should be treated as resolved-negative for planning purposes: the original package is stalled past v3, and its community fork explicitly limits itself to bug fixes on the old major version — not a safe long-term bet for a from-scratch app in 2026. objectbox is actively maintained and fast but has a NoSQL object-store shape (a bigger conceptual jump from Drizzle/SQL than drift) and a less transparent migration story for renames. sqflite is a solid, actively maintained low-level primitive but offers no relational/ORM ergonomics on its own — it is more a building block (drift itself can use it as a backend) than a complete replacement for the current Drizzle layer.
