# Flutter build/release pipeline & GitHub Actions macOS runner capabilities

Research date: **2026-07-25**. All pages below were fetched live on this date; version numbers and "current" status reflect that date, not historical/cached knowledge. Flutter docs pages fetched showed a "Flutter version 3.44.7" banner and per-page last-updated dates noted inline.

## Top-line findings / blockers

- **Android-emulator-on-macOS-runner nested-virtualization limitation is still real in 2026, and is now arguably worse, not better.** GitHub's current default hosted macOS runner (`macos-latest` → `macos-26`, Apple Silicon/arm64) explicitly does **not** support nested virtualization: "Nested-virtualization is not supported due to the limitation of Apple's Virtualization Framework" ([GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), fetched 2026-07-25). A fresh 2026 feature request asking GitHub to enable Apple's newer nested-virtualization APIs (available since macOS 15) on arm64 runners was opened 2026-01-08 and **closed as "not planned"** ([actions/runner-images#13505](https://github.com/actions/runner-images/issues/13505)). So this is not stale 2022-era information — it is the current, confirmed 2026 state.
- Intel-based macOS runners (`macos-15-intel`, `macos-26-intel`, the "-large"/x64 labels) are not blocked by the nested-virtualization restriction the same way, but community reports (including a maintained discussion on the most popular Android-emulator GitHub Action) show the HAXM kernel extension "not approved to load" in CI and flaky results even where Hypervisor.Framework nominally provides acceleration ([ReactiveCircus/android-emulator-runner Discussion #286](https://github.com/ReactiveCircus/android-emulator-runner/discussions/286)). They are also the pricier, lower-CPU-count runner tier.
- The authoritative community tooling for this (ReactiveCircus/android-emulator-runner, the de facto standard Action) now explicitly tells users: **"It is now recommended to use the Ubuntu (`ubuntu-latest`) runners which are 2-3 times faster than the macOS ones which are also a lot more expensive."** ([android-emulator-runner README](https://github.com/ReactiveCircus/android-emulator-runner/blob/main/README.md)). Linux GitHub-hosted (including larger) runners get genuine hardware-accelerated Android virtualization via KVM ([GitHub Changelog, 2023-02-23](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) — Linux acceleration announcement).
- **Recommended CI shape:** don't try to run the Android emulator and iOS Simulator accelerated in one macOS job. Run iOS Simulator + `integration_test` on a macOS runner, and run the Android emulator + `integration_test` on a Linux runner with KVM enabled, as two parallel jobs in one `workflow_dispatch`-gated workflow. Both can live in the same workflow file, triggered only manually, separate from the Linux-only unit-test CI that runs on every push.
- **Part 1 pipeline decision for a small team/solo dev:** Flutter's own official CI/CD doc treats Fastlane + a CI-native platform (it names Codemagic/Bitrise/Appcircle) as the two supported paths, and explicitly does **not** cover a "pure manual" path as a recommended production workflow beyond local testing ([docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd)). For a solo developer/small team shipping to both stores, **Codemagic's built-in Flutter support + built-in code-signing management** has materially lower setup cost than **Fastlane + `match` + `supply`**, which in turn is far lower cost than fully manual cert/keystore handling repeated for every release. Manual is fine for the very first TestFlight/internal build but doesn't scale even to a two-person team.

## Part 1: Signing/Release Pipeline

### Manual cert/keystore management (Flutter's own docs)

- **iOS**: `flutter build ipa` produces an `.xcarchive` in `build/ios/archive/` and an `.ipa` in `build/ios/ipa`. Signing is handled through Xcode's "Automatically manage signing" toggle in Signing & Capabilities (on by default), which Flutter's docs say is "sufficient for most apps." For anything beyond that, the docs punt to Apple's own docs (Apple's [Code Signing Guide](https://developer.apple.com/library/content/documentation/Security/Conceptual/CodeSigningGuide/Introduction/Introduction.html) and [Create, export, and delete signing certificates](https://help.apple.com/xcode/mac/current/#/dev154b28f09)) rather than documenting manual cert/profile management itself. Source: [docs.flutter.dev/deployment/ios](https://docs.flutter.dev/deployment/ios), page last updated 2026-05-05.
- **Android**: Flutter's docs walk through generating an upload keystore with `keytool` (or Android Studio), writing `android/key.properties` (explicitly warned not to commit to source control), and wiring it into `android/app/build.gradle.kts`. `flutter build appbundle` then produces a signed `.aab`. Google's **Play App Signing** is referenced as the recommended key-management model but implementation detail is deferred to Google Play's own docs — Flutter's page does not itself cover CI or Fastlane integration at all ("Not mentioned" in that doc). Source: [docs.flutter.dev/deployment/android](https://docs.flutter.dev/deployment/android), page last updated 2026-06-26.
- **Setup cost / small-team suitability**: Lowest initial cost (no third-party tool to learn), but it does not scale: every teammate needs the shared `.jks`/passwords out-of-band for Android, and iOS's "Automatic signing" model only works cleanly for a single Apple ID signed in on one machine — a second developer or a CI machine re-triggers Apple Developer Portal certificate/profile churn. Flutter's own CI/CD doc treats this as a local-only step, saying teams should "test the build and deployment process locally before migrating to a cloud-based system" and then move to Fastlane or an all-in-one platform for the actual pipeline ([docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd)).

### Fastlane (`match` for iOS, keystore/`supply` for Android)

- **What `match` does**: centralizes iOs certs/provisioning profiles in one shared, encrypted store (git repo with OpenSSL encryption, Google Cloud Storage, or Amazon S3) so every developer and every CI machine pulls the same identity instead of each generating their own. It can auto-repair expired/invalid certs and profiles. Setup is `fastlane match init` → choose storage backend → `fastlane match appstore` / `fastlane match development` thereafter. Source: [docs.fastlane.tools/actions/match](https://docs.fastlane.tools/actions/match/), doc build date 2026-07-06.
- **iOS setup path**: install Xcode command-line tools, install fastlane via Bundler (`gem "fastlane"` in a `Gemfile`, `bundle exec fastlane …` — the docs actively recommend Bundler over `gem install fastlane`/Homebrew for reproducibility), then `fastlane init` to scaffold `fastlane/Fastfile`/`Appfile`. Ruby 3.3+ is the recommended interpreter (3.0+ is the floor; 3.1 and earlier trigger deprecation warnings). Source: [docs.fastlane.tools/getting-started/ios/setup](https://docs.fastlane.tools/getting-started/ios/setup/), doc build date 2026-07-06.
- **Android signing / `supply`**: Flutter's own CI/CD doc (not Fastlane's own pages, which weren't asked for `supply` specifically) documents the pattern actually used in practice: keep the upload keystore off the CI box, inject it as a base64 secret, decode it at build time (`echo "$PLAY_STORE_UPLOAD_KEY" | base64 --decode > …`), and feed the Play Store service-account JSON to `upload_to_play_store(json_key_data: ENV['…'])` via env var rather than a checked-in file. Source: [docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd).
- **Setup cost / small-team suitability**: Meaningfully more setup than "do nothing" (installing Ruby/Bundler/fastlane, learning Fastfile/Matchfile syntax, choosing and provisioning a `match` storage backend, wiring secrets into whichever CI you use), but it is a **one-time** cost and Fastlane's own docs frame it as low-complexity for a solo dev or small team: "a solo developer or small team needs to: create one shared Apple ID (optional but recommended), set up storage backend access, run match init and periodic syncs." It removes the single-point-of-failure risk of one person's laptop holding the only signing identity, and it is CI-agnostic (works from GitHub Actions, Codemagic, Bitrise, etc., since it's just Ruby/CLI). Flutter's official cookbook explicitly recommends this route for teams integrating with an *existing* CI system, and separately warns that CI instances are "ephemeral and untrusted" so credentials should never be left on the build server (source: [docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd)).

### Codemagic (Flutter-specific CI with built-in signing)

- **Flutter-native support**: Codemagic supports Android, iOS, web, macOS, Linux, and Windows Flutter build targets, with per-platform build-mode options and, per its own docs, "flutter build ipa command is available as of Flutter version 1.24.0-6.0 and is the recommended option" for iOS archives. It has direct publish integrations to App Store Connect and Google Play built into the workflow editor. Source: [docs.codemagic.io/flutter-configuration/flutter-projects](https://docs.codemagic.io/flutter-configuration/flutter-projects/), page last updated 2026-06-26. It listed available Xcode versions on its macOS build machines ranging **16.0.x through 27.0.x (edge)** as of that fetch.
- **iOS signing**: two supported modes — (1) automatic, via an App Store Connect API key with "App Manager" role, where Codemagic fetches matching certs/profiles itself; or (2) manual upload of `.p12` certs and `.mobileprovision` files, referenced by name in `codemagic.yaml`. Team-admin permission is required to upload/edit signing files (view-only for other members). Source: [docs.codemagic.io/yaml-code-signing/signing-ios](https://docs.codemagic.io/yaml-code-signing/signing-ios/), page last updated 2026-06-05.
- **Android signing**: upload (or generate in-tool via keytool) a keystore once; Codemagic stores it server-side under "Code signing identities" (admin-controlled access) and auto-injects `CM_KEYSTORE_PATH`, `CM_KEYSTORE_PASSWORD`, `CM_KEY_ALIAS`, `CM_KEY_PASSWORD` env vars that you reference from `build.gradle`. Note: "the uploaded keystore cannot be downloaded from Codemagic," so you must keep an independent backup. Source: [docs.codemagic.io/yaml-code-signing/signing-android](https://docs.codemagic.io/yaml-code-signing/signing-android/), page last updated 2025-02-18 (oldest-dated Codemagic page checked, but describes the current mechanism — no newer contradicting page found).
- **Setup cost / small-team suitability**: Lowest ongoing operational cost of the three options for a solo dev/small team — no Ruby toolchain, no separate storage backend to provision for certs, no self-hosted secrets rotation logic; everything lives in one UI with role-based access already built for "admin can upload, others can only view." Flutter's own CI/CD cookbook lists Codemagic (alongside Bitrise/Appcircle) as having "built-in Flutter functionality" and recommends it as the all-in-one path, versus Fastlane which it frames as the option for teams integrating with an existing generic CI provider. Source: [docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd). Trade-off: vendor lock-in to Codemagic's yaml/UI, and cost (Codemagic is a paid product beyond its free tier), versus Fastlane/match being free and portable across any CI, and manual being free but not team-safe.

### Other CI-native tooling worth noting

- **Codemagic CLI Tools**: Flutter's own iOS deployment doc calls out an alternative workflow using Codemagic's CLI tools package, which gives "full control of distribution certificates in a temporary keychain" isolated from the login keychain — usable even outside Codemagic's hosted CI (e.g., in a self-hosted or GitHub Actions runner) to avoid manual Keychain fiddling. Source: [docs.flutter.dev/deployment/ios](https://docs.flutter.dev/deployment/ios).
- **Xcode Cloud**: Flutter's CI/CD cookbook documents Xcode Cloud as a viable path requiring Xcode 13.4.1+ and an Apple Developer Program enrollment, with post-clone script hooks (env vars like `$CI_PRIMARY_REPOSITORY_PATH`) needed to run `flutter build` since Xcode Cloud doesn't know about Flutter natively. Source: [docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd). This only covers iOS — Android still needs a separate pipeline, so it doesn't solve both stores from one system the way Codemagic does.
- **GitHub Actions marketplace / raw App Store Connect & Google Play APIs**: not covered by name on the Flutter cookbook page beyond "Fastlane can be integrated with GitHub Actions" (with a linked example project). Using the App Store Connect API / Google Play Developer API directly (bypassing Fastlane) is possible but is DIY scripting with no official Flutter-blessed wrapper — higher effort than any of the above for a small team, not recommended as a first choice.

### Comparison summary

| Option | One-time setup cost | Ongoing/team cost | Small-team/solo fit |
|---|---|---|---|
| Manual (Xcode auto-signing + hand-built keystore) | Lowest | High — breaks down beyond 1 person/machine, CI needs manual cert export | OK for solo dev's very first build only |
| Fastlane + `match` (+ scripted Play upload) | Medium (Ruby/Bundler/Fastfile/Matchfile + storage backend) | Low once set up; free; portable across any CI | Good — Fastlane's own docs describe this as low-complexity for solo/small teams |
| Codemagic (built-in signing + Flutter support) | Low (all in web UI, no local toolchain) | Low; paid product; some vendor lock-in | Best fit for small team/solo wanting least ceremony |
| Xcode Cloud / raw store APIs | Medium–high | iOS-only (Xcode Cloud) or fully DIY (raw APIs) | Not recommended as the primary path for dual iOS+Android releases |

## Part 2: GitHub Actions macOS Runner Capabilities

### Current image lineup (fetched 2026-07-25)

- Per the `actions/runner-images` repo's images table, current macOS labels are: **`macos-26-arm64-Readme.md`** → labels `macos-latest`, `macos-26`, `macos-26-xlarge` (Apple Silicon/arm64); **`macos-26-Readme.md`** → labels `macos-latest-large`, `macos-26-intel`, `macos-26-large` (Intel/x64); and **`macos-15` / `macos-15-arm64`** readmes for the previous generation. `macos-14` (both arch variants) is marked deprecated. Source: [actions/runner-images](https://github.com/actions/runner-images).
- Official spec confirmation from GitHub's own docs: `macos-latest`/`macos-26` = 3 CPUs (M1-class Apple Silicon), 7 GB RAM, arm64; `macos-15-intel`/`macos-26-intel` = 4 CPUs, 14 GB RAM, x64. Source: [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), fetched 2026-07-25.
- Note the naming: Apple's OS versioning jumped to match calendar year (macOS 26 "Tahoe"), so "macos-26" is the current/latest generation in 2026, not a typo — `macos-latest` now resolves to it.

### Xcode / Android SDK versions preinstalled (macos-26-arm64 image, the current `macos-latest`)

- **Xcode**: 26.0.1, 26.1.1, 26.2, 26.3, 26.4.1, 26.5 (default), 26.6 all present. Source: [actions/runner-images/.../macos-26-arm64-Readme.md](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md).
- **Android tooling** (yes — Android SDK is preinstalled on the macOS image, not just Linux images): Android Command Line Tools 16.0; Android Emulator 36.6.11; Platform-Tools 37.0.0; NDK 27.3.13750724 (default), 28.2.13676358, 29.0.14206865; build-tools 35.0.0/35.0.1/36.0.0/36.1.0/37.0.0; SDK platforms android-35/36/36.1/37/37.1. Source: same runner-images macOS readme.

### Can a macOS runner run Android emulator + iOS Simulator in one job?

- Nothing prevents *installing/launching* both in one job — the SDKs coexist on the image. The real constraint is **acceleration**, not existence: the iOS Simulator is native to macOS and always runs full-speed; the Android emulator's speed depends on the same nested-virtualization/Hypervisor path that GitHub's own docs say is unsupported on the current (arm64) macOS runner (see below). So technically yes, functionally you'd get a working-but-very-slow (software-rendered) Android emulator alongside a fast iOS Simulator in the same job — not a good trade for CI time/cost.
- Flutter's own official CI/CD cookbook gives **no guidance at all** on running `integration_test` against emulators/simulators in CI — it only covers build/release pipelines (Fastlane, Codemagic, Xcode Cloud). Source: [docs.flutter.dev/deployment/cd](https://docs.flutter.dev/deployment/cd), checked 2026-07-25. This is a genuine gap in official docs; the emulator/CI design has to be assembled from GitHub's own runner docs plus third-party Actions (e.g., `reactivecircus/android-emulator-runner`), not from Flutter's docs.

### Nested virtualization / hardware acceleration for Android emulator on macOS runners — CURRENT 2026 STATUS

This is confirmed **still an active limitation, not resolved**, as of 2026-07-25:

- GitHub's own current reference doc states plainly: **"Nested-virtualization is not supported due to the limitation of Apple's Virtualization Framework."** Source: [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), fetched 2026-07-25. This applies to the arm64 macOS runners, i.e., today's `macos-latest`/`macos-26`.
- This is not just an old carry-over statement: a feature request specifically asking GitHub to adopt Apple's newer Hypervisor.framework nested-virtualization APIs (added starting macOS 15.0, per Apple's own API additions `hv_vm_config_set_el2_enabled` and `isNestedVirtualizationEnabled`) was opened **2026-01-08** and was **closed as "not planned"**. Source: [actions/runner-images#13505 "Support the hypervisor.framework on Apple-silicon"](https://github.com/actions/runner-images/issues/13505). So as of mid-2026, GitHub has had the opportunity to lift this restriction on newer macOS and has explicitly declined.
- Intel-based macOS runners (`macos-15-intel`/`macos-26-intel`) aren't blocked by that specific nested-virtualization restriction, and Android's own emulator docs describe macOS falling back through Apple's built-in Hypervisor.Framework (with HAXM only as a legacy fallback: "on Mac OS X v10.10 Yosemite and higher, the Android Emulator uses the built-in Hypervisor.Framework by default, and falls back to using Intel HAXM if Hypervisor.Framework fails to initialize"). But in practice on GitHub-hosted Intel macOS runners, the community has documented the HAXM kernel extension failing to load in CI ("Extension ... not approved to load. Please approve using System Preferences" — not grantable non-interactively) and flaky emulator behavior even where Hypervisor.Framework nominally engages. Source: [ReactiveCircus/android-emulator-runner Discussion #286 "Hardware acceleration"](https://github.com/ReactiveCircus/android-emulator-runner/discussions/286).
- The de facto standard community Action for this now tells users outright to avoid macOS for this purpose: **"It is now recommended to use the Ubuntu (`ubuntu-latest`) runners which are 2-3 times faster than the macOS ones which are also a lot more expensive."** Source: [ReactiveCircus/android-emulator-runner README](https://github.com/ReactiveCircus/android-emulator-runner/blob/main/README.md).
- By contrast, Linux GitHub-hosted runners (including the larger/paid tier) do get real KVM-backed hardware acceleration for the Android emulator, a capability GitHub added and documented ([images/macos/macos-26-arm64-Readme.md references the emulator tooling](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md); the Linux-acceleration rollout itself is GitHub's 2023 changelog entry on hardware-accelerated Android virtualization for Windows/Linux larger runners).

**Conclusion for the pipeline design**: treat "run Android emulator and iOS Simulator accelerated in the same macOS job" as not viable in 2026. The workable pattern is two separate jobs in one workflow — a `macos-latest` job for `flutter test integration_test` against the iOS Simulator, and a `ubuntu-latest` job (with KVM enabled per the `reactivecircus/android-emulator-runner` Action's setup instructions) for the same suite against the Android emulator — both gated behind `workflow_dispatch` in a workflow file separate from whatever Linux-only job runs unit tests on every push.

### `workflow_dispatch` gating mechanics

- `workflow_dispatch` is GitHub's manual-trigger event; it must be present in the workflow YAML (`on: workflow_dispatch:`) to enable a "Run workflow" button in the Actions UI. It supports up to 25 top-level custom inputs, with a combined payload limit of 65,535 characters, and — importantly — **the workflow file must exist on the repository's default branch** for the manual trigger to be available at all. Source: [Events that trigger workflows — workflow_dispatch](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#workflow_dispatch), fetched 2026-07-25.
- It can coexist with other triggers in the same file (e.g., `on: { push:, workflow_dispatch: }`) — but for this use case (keeping the slow/expensive emulator+simulator job fully separate from a Linux push-triggered CI job), the cleaner design is a **dedicated workflow file** containing only `workflow_dispatch:` as its trigger, rather than layering it onto the existing push-triggered CI workflow. Same source.
