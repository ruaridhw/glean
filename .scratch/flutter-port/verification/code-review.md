## Verdict: **CHANGES REQUESTED**

Two findings block merge, and both share the same shape: correct, tested code that a real user can never reach because nothing wires it into the flow that would call it. (1) The entire first-run onboarding flow — fully built, fully unit-tested — is never mounted anywhere in the app. (2) Manually adding a recipe to the plan from its detail screen (the primary, everyday way meals get planned) never creates the shopping-list rows for what the pantry can't cover — that logic exists and is correct, but only the bulk "Generate" path calls it. Both fixes are small and I've stated exactly what's missing.

Everything else I dug into — checkout partial-match, user isolation, rollover idempotency, cooked/undo, the router, and the Riverpod conventions — is genuinely strong, and I could not find a third issue of comparable severity anywhere in the data layer. Once both are wired and verified through a real-navigation/real-mutation test (not the isolated unit tests that already pass), I'd expect to approve.

## Blocking findings

### 1. First-run onboarding is fully built and tested, but never reachable through real navigation

`lib/features/onboarding/onboarding_gate.dart:1-18` — the class's own doc comment says so directly: *"nothing in `lib/router/**` currently mounts this... Until that one-line change lands, `OnboardingScreen` is fully built and tested in isolation ... but unreachable through real navigation."* I confirmed this by reading the actual composition, not just the comment:

- `grep -rn "OnboardingGate" lib/` finds it only in its own file — it is never instantiated anywhere.
- `lib/router/router.dart:142-148`: the `StatefulShellRoute.indexedStack` builder returns `AppShell(navigationShell: navigationShell)` directly — no `OnboardingGate` wrapper.
- `lib/app.dart:19-34` (`GleanApp`) wraps nothing either; it just hands `goRouterProvider`'s router straight to `MaterialApp.router`.
- Every onboarding test (`test/features/onboarding/**`) pumps `OnboardingScreen`/`OnboardingGate` directly under a bare `MaterialApp`/`ProviderScope`, never through `goRouterProvider`. No test under `test/router/**` mentions `Onboarding` at all.

**Failure scenario:** a brand-new user signs in for the first time. Per `FLUTTER_MIGRATION.md` §6 Cross-cutting, they should see a short, skippable setup for dinners/week, servings and dietary flags before landing on Pantry. Instead they land on Pantry immediately. `mealsPerWeek`, `preferredServings`, and `dietaryFlags` stay at their compile-time defaults forever, because nothing else in the app ever writes them — this is verbatim the RN-app defect §6 states as the reason onboarding exists ("There is no onboarding today, so these values ... stay at defaults forever"). `flutter test` stays green throughout, because every onboarding test deliberately bypasses the real app shell — the gap is invisible to the suite.

This is the same shape of failure as `FINDINGS.md` F-16 (a screen built and tested in isolation, but the one integration step nobody owned never happened) — except here it's a whole feature, and unlike F-16, no router-level test would have caught it, because the route table itself is unaffected; only `app.dart`/`router.dart`'s *composition* is missing.

**Fix**, per the doc comment already in the codebase: wrap the shell builder's return value as `OnboardingGate(child: AppShell(navigationShell: navigationShell))` in `lib/router/router.dart`. I'd also want one test that pumps the real router as a first-run user (`hasCompletedOnboardingProvider` resolving `false`) and asserts `OnboardingScreen` renders before `PantryScreen` — none of the existing isolated tests would catch a regression here.

### 2. Manually adding a recipe to the plan never creates its shopping-list gaps — the same logic exists and is correct, but only one of its two call sites uses it

`ShoppingRepository.addGapsForRecipe` (`lib/data/repositories/shopping_repository.dart:131-191`) computes, per non-optional recipe ingredient, whether the pantry falls short for the given servings and inserts a shopping row for exactly the shortfall — this is real, correct, tested logic (`test/features/shop/plan_rows_test.dart`). `grep -rn "addGapsForRecipe" lib/` shows it is called from exactly one place: `generate_week_controller.dart:189-196`, inside the bulk "Generate" flow's `_persist` loop.

The other, more common way a meal enters the plan — tapping "Add to plan" on a recipe's own detail screen — does not call it. `lib/features/meals/saved_recipe_detail.dart:169-201` (`_onAddToPlan`) checks plan-full/already-planned, then calls only `planRepository.addEntry(...)`. It never touches `ShoppingRepository`.

**Failure scenario:** a user searches for a recipe, opens it, and taps "Add to plan" (the single most direct path to planning a meal in this app, and the one `saved_recipe_detail.dart`'s own doc comment calls out as the AC-MEAL-08/09 flow). The recipe needs 400g of chicken breast; the pantry has none. The plan entry is created — the button correctly flips to "In plan" — but no shopping-list row is ever created for the missing chicken. The user has no way to know the plan now depends on an ingredient they don't have and haven't been told to buy, until they try to cook it. This is silent in exactly the way §11's bug catalogue calls out ("Announce plan-derived shopping rows (silently inserted today)") — except here the row isn't even inserted silently, it's simply never inserted, for the majority of how meals get planned.

**Fix:** call `ShoppingRepository.addGapsForRecipe` from `_onAddToPlan` too, the same way `generate_week_controller.dart` does. Keep it idempotent against `FINDINGS.md`'s F-05 concern (the RN duplicate-add bug produced duplicate shopping gaps alongside duplicate plan entries) — `addGapsForRecipe`'s existing "skip if an unchecked row for this ingredient already exists" check (`shopping_repository.dart:167-175`) should already cover this, but it's worth a test that adds the same recipe to the plan twice and asserts the gap row isn't duplicated.

## Non-blocking findings

### 3. `restoreFromCook` clobbers `lastUsedAt` when two plan entries share an ingredient and are undone out of order — reproduced

`lib/data/repositories/pantry_repository.dart:369-409`. `markCooked`/`undoCooked` restore *quantity* correctly (addition/subtraction is order-independent), but `restoreFromCook` unconditionally overwrites `lastUsedAt` with the value captured at the time of *that specific entry's* cook, regardless of what's happened to the row since. I reproduced this with a throwaway test (written, run, and deleted — `git status` is clean): cook entry A for "chicken breast" (records `previousLastUsedAt = null`), cook entry B for the same ingredient a day later (records `previousLastUsedAt = <A's cook time>`, sets the row's `lastUsedAt` to B's time), then undo A. Quantity restores correctly (900g, as expected), but `lastUsedAt` resets to `null` — erasing B's still-in-effect, more-recent cook. `lastUsedAt` only feeds pantry sort order (`watchAll`'s tie-break, `pantry_repository.dart:87-99`) and the urgency score in `compression.dart`, so this is a ranking/staleness-scoring inaccuracy, not data loss. No existing test covers two plan entries sharing an ingredient with an out-of-order undo — all `markCooked`/`undoCooked` tests in `test/data/plan_repository_test.dart` use a single entry per ingredient.

### 4. Fire-and-forget mutation helpers have no error path — reproduced, and it's an inconsistent pattern against the rest of the codebase

Every delete/undo/toggle helper in `lib/features/{pantry,shop,plan,meals}/actions.dart` (e.g. `deletePantryItemWithUndo`, `deleteShoppingItemWithUndo`, `markCookedWithUndo`, `deleteRecipeWithUndo`) is invoked as `onDelete: () => someAsyncAction(...)` — no `await`, no `try/catch`, no `unawaited()` at the call site (e.g. `lib/features/pantry/widgets/pantry_section_view.dart:55`, `lib/features/plan/widgets/plan_slot_row.dart:27`, `lib/features/shop/widgets/shop_list_section.dart:85`). There's no `runZonedGuarded`/`PlatformDispatcher.instance.onError` anywhere in `lib/main.dart`/`bootstrap.dart`. I forced this: closed the in-memory drift database mid-test, then swiped a pantry row. The write throws a `StateError` that propagates as an uncaught async rejection with `EXCEPTION CAUGHT BY FLUTTER TEST FRAMEWORK` — no snackbar, no recovery, and it happened *after* `Dismissible` had already committed to removing the row, so a real device would be one `pumpAndSettle` away from `Dismissible`'s own "still part of the tree" assertion the next time that key rebuilds. This is a real but rare trigger (local SQLite writes essentially never fail), so I'm not calling it blocking — but it's worth naming as an **inconsistent pattern**, not just an edge case: `Settings._persist` (`settings_screen.dart:115-126`), `OnboardingScreen._finish` (`onboarding_screen.dart:61-84`), `ReviewScreen._confirm` (`review_screen.dart:87-105`), and the Plan-generation path (`plan_screen.dart:104-120`, via `ref.listen`) all `try`/`catch` and surface a snackbar on failure — but the swipe-delete/undo/mark-cooked family across all four features never does. One of these two patterns should win everywhere; right now the codebase has both.

### 5. `ShoppingRepository.checkOffResolvedIngredients` (AC-SHOP-04) is fully built and tested, but has zero production call sites

`lib/data/repositories/shopping_repository.dart:198-210`, tested at both the data layer (`test/data/shopping_repository_test.dart:91`) and in a dedicated feature test (`test/features/shop/scoped_checkoff_test.dart`, whose own docstring says it fires "when a scanned receipt resolves an ingredient, to tick off the matching shopping row even if the user hadn't ticked it themselves"). `grep -rn "checkOffResolvedIngredients" lib/` finds only its own definition and a doc-comment mention in `actions.dart:20` — no screen or action ever calls it. The receipt-into-shop flow (`lib/features/intake/review_screen.dart:138-145`, `_confirmPantry`) only calls `resolveCheckout`, which deletes rows that are *already checked* and receipt-matched — it never ticks an unchecked-but-matched row. `review_screen.dart:120-121`'s own comment says "checked off (AC-SHOP-01)" describing this call, which is misleading: the code deletes, it doesn't check off. I'm flagging this with real hedging: `ACCEPTANCE.md`'s literal AC-SHOP-04 wording ("Check-off by ingredient is scoped...") doesn't explicitly require a call site, and AC-PAN-11 explicitly forbids touching the shopping list on an ordinary (non-`returnToShop`) pantry review — so it's plausible this method is an intentionally-ported-but-superseded utility rather than a missing wire-up. Either way, it's dead code today, and the comment that name-drops it should say what the code actually does.

### 6. Onboarding-completion state is persisted to a plain text file, outside SQLite — a real spec-fidelity gap

`FileOnboardingStatusStore` (`lib/features/onboarding/providers/onboarding_status.dart:41-75`) writes completed user ids to `onboarding_completed.txt` in the app documents directory via `path_provider`, one id per line, and reads the whole file back on every `watch()`/`markCompleted()`. `FLUTTER_MIGRATION.md` §3 states plainly: "local SQLite is the sole source of truth for user data." This is user data (whether onboarding is done) living outside it. It's correctly scoped per-user (no cross-user leak — I checked `_readCompletedIds`/`markCompleted` key strictly by the id passed in), so this isn't a data-isolation bug, just an architecture-principle violation. The file's own doc comment is upfront about why: `user_config` had no column for this and `lib/data/**` was owned by another wave being edited concurrently, so this wave built a self-contained stopgap "designed to be swapped for a `UserConfigRepository`-backed implementation later without any call site changing." That swap hasn't happened. Worth doing before ship — a text file with no schema, no migration path, and no transactional guarantee is a worse long-term home for this than the column it was always meant to be.

## What's genuinely good

- **The checkout/rollover/cooked-undo core is excellent.** `resolveCheckout`, `rolloverUncookedMeals`, and `markCooked`/`undoCooked` (`shopping_repository.dart`, `plan_repository.dart`) are precisely scoped, transactional where it matters (I confirmed `PantryRepository.addItems` and `ShoppingRepository.addAiItems` really do wrap their loops in `_db.transaction()`, not just claim to in a comment), and tested against real post-mutation state — exact row sets, exact quantities, exact idempotency (`rollover ... running it twice does not duplicate entries`) — never a mocked query-builder call count.
- **User-scoped isolation is airtight everywhere I checked.** Every repository method takes and filters by `userId`; `test/data/user_isolation_test.dart` proves cross-user writes and reads have no effect, including the "same ingredient name resolves to the same shared catalog row, but pantry/plan/shopping rows stay separate" case.
- **Test quality is consistently real-outcome**, not the RN suite's query-builder-call-shape antipattern. I read the checkout partial-match test, the user-isolation tests, the rollover-idempotency tests, and the cooked/undo tests in full: all assert actual persisted state (row counts, specific quantities, specific ids) through a real in-memory drift database, not mocked call shapes. I found no vacuous test in the areas I checked in depth.
- **The local-write vs. remote-command split is applied uniformly.** Local mutations go straight through repository providers with no intermediate `AsyncNotifier` layer (pantry/shop/plan/meals `actions.dart`); every remote call is an `AsyncNotifier.autoDispose` command provider guarded by `ref.keepAlive()` for its network duration (`lib/api/providers/*.dart`). Same shape in all four features — not reinvented per module.
- **House rules held up under grep**: zero `cupertino.dart` imports, zero direct `drift`/API-client imports from `lib/features/**`, zero `ref.invalidate` calls, no screen file over 250 lines, haptics fired only through the design-system ladder (`Haptics`/`hapticsProvider`), no hand-rolled `AnimationController` loops (`SkeletonBox` genuinely uses `TweenAnimationBuilder`, `SwipeToDeleteRow` genuinely uses `Dismissible`).

## Answers to the three architecture questions

**Is the router set up right?** Yes. `StatefulShellRoute.indexedStack` for the five tabs with independent per-branch back stacks, intake and sign-in as top-level siblings outside the shell (so the tab bar structurally cannot render over the camera — not just styled to look like it doesn't), a reactive auth redirect via `refreshListenable` gating only on `signedOut` (never `expired`, per spec §5), and route constants centralized in `AppRoutes` with structural tests (`route_table_test.dart`) rather than text-based ones. The one real gap isn't in the router table — it's that `router.dart`/`app.dart` never compose in `OnboardingGate` (blocking finding #1), a missing piece of composition next to the router rather than a flaw in the routing design itself. `RecipePreviewScreen`'s deliberate, documented bypass (#11) is the only other deviation from "the router owns navigation," and it's a defensible, tested exception rather than an inconsistency.

**Is state management set up right?** Yes, consistently. Riverpod is used exactly as the spec intends: `StreamProvider` over drift `.watch()` for every screen read (no manual reload, no invalidation anywhere I could find), plain repository calls for local mutations, and `AsyncNotifier.autoDispose` + `ref.keepAlive()` for every remote command — applied identically across Pantry, Shop, Plan, and Meals rather than four half-solutions. Errors from remote commands are surfaced via `ref.listen` at the screen level (`plan_screen.dart:104-120`), not swallowed. The soft spot is finding #4: local-mutation error handling has no equivalent safety net across the swipe/undo/mark-cooked family, which is a gap in the *error-path* half of the pattern, not the read/command split itself.

**Are components reused where they should be, and not where they shouldn't?** Mostly yes, with one clear miss. `Dismissible`-backed `SwipeToDeleteRow`, one `ReviewScreen` for both pantry and shop intake (parameterised by `destination`), `IntegerSliderControl` shared by Settings and onboarding, and `describe_form.dart` (the shared presentational shell for pantry/shop describe, per F-16's resolution, which deliberately kept separate provider wiring for each screen rather than forcing a generic widget over a real ~15-line difference) are all genuine one-implementation reuse where the RN app had duplicates. `Badge` stays bespoke as the spec sanctions, and themed `FilledButton`/`OutlinedButton`/`TextButton`/`Chip` show up consistently rather than hand-rolled pill `Pressable`s. The clear miss is finding #2: `PlanRepository.addEntry` has two call sites that both create a plan entry from a recipe — `generate_week_controller.dart` and `saved_recipe_detail.dart` — and only one of them also calls `ShoppingRepository.addGapsForRecipe` to keep the shopping list in sync. That's the exact "two ways of doing one thing" pattern the brief asked me to look for, just expressed as an omission rather than a duplicate implementation. `OnboardingScreen` (#1) and `checkOffResolvedIngredients` (#5) are the other two cases of correctly-built, non-duplicated logic that nothing ever calls.

### The canonical-unit fix (R-18) — the one you asked me to scrutinise specifically

**The corruption bug itself is genuinely and correctly fixed.** `ingredients.canonicalUnit` is now set on first resolution (`ingredients_repository.dart:80-135`, `canonicalUnitFor` in `unit_normalization.dart:65-78`), `PantryRepository._upsert` re-normalises against the *pantry row's own* unit before merging and throws `PantryUnitMismatchException` rather than summing when no conversion exists (`pantry_repository.dart:295-335`), and it's tested end-to-end: "2 kg then 500 g" now totals 2500 g (`test/data/pantry_repository_test.dart`, the exact R-18 regression case), and a genuinely incompatible merge (garlic first as `'units'`, then `50 g`) throws and leaves the original row untouched. I also checked the RN-parity claim in the commit message directly — `git show 906c9bb^:mobile/src/db/ingredients.ts` confirms the original app never wrote `canonical_unit` either, so this is correctly attributed as a pre-existing defect, not something the port introduced.

**Throwing over silently summing is the right instinct** — a wrong number that looks plausible is worse than a loud failure, and the "first real unit wins and stays" rule is at least *consistent*: it mirrors the existing "first real category wins and stays" rule in the same method, rather than inventing a second convention.

**But the fix has a real, traceable follow-on gap, and it just got wider in this same diff.** The rule's soundness depends on the *first* unit an ingredient is ever resolved with being a meaningful choice — and one of the call sites feeding it is not a choice at all, it's a fallback for missing data: `review_screen.dart:163-164`'s `_unitOrDefault` turns a blank parsed-unit field into `'units'` before it ever reaches `PantryRepository.addItem`. A blank unit on a parsed receipt/describe line for a count-style item (a very ordinary LLM-parse outcome — "3 apples" with no unit token) is exactly the kind of ingredient that later gets bought by weight on a different receipt. Once that first blank-unit add locks `canonicalUnit` to `'units'`, it is **permanent and has no in-app recovery path** — there is no UI affordance to reset an ingredient's canonical unit, and `QuantityEditSheet.updateItem` writes a pantry row's `unit` field directly with no normalisation at all, so it can't fix the underlying ingredient-level lock either. Every future add of that ingredient in a real mass/volume unit throws.

Three things compound this beyond what the fix's own tests show:
1. **This diff extends the same `unit:` seeding to `ShoppingRepository.addManualItem`/`addAiItems`** (`shopping_repository.dart:64-116`) — so an ingredient can now have its canonical unit locked from the *shopping* side too (an AI-parsed shopping item's unit also defaults blank text to `'units'`, per the existing fallback in `addAiItems`), before it's ever been near the pantry. The surface this can trigger from just grew, in the same change that fixed the original bug.
2. **The catch site gives no actionable signal.** `review_screen.dart:100-105` and `manual_entry_screen.dart:69-71` both catch *any* exception from the commit path with the same generic "Could not save. Try again." / "Could not save this item. Try again." A `PantryUnitMismatchException` is not a transient failure — retrying the identical input fails identically, forever — but the user is told to do the one thing guaranteed not to work, with no indication of which item or unit is the problem.
3. **`PantryRepository.addItems` commits the whole review batch as one transaction** (confirmed still true, unchanged from the original review). One poisoned ingredient anywhere in a 12-item receipt-scan batch fails the *entire* confirm, and the generic error message gives no way to identify which row to remove to make progress.

I want to be precise about what I'm asserting and what I'm not: `test/data/pantry_repository_test.dart`'s "a genuinely incompatible unit merge throws" test proves the team deliberately chose and tested this exact throw behaviour — this is not an oversight in the sense of an untested branch, it's a considered design that I think under-weighs the recoverability side of the trade-off. I'm not asserting users will hit this constantly; I'm asserting the trigger (a blank/count unit on a first resolution, later contradicted by a real unit) is ordinary and plausible, not contrived, and that the current failure mode when it happens is a dead end with a misleading message, which is precisely the class of thing FLUTTER_MIGRATION.md §11 exists to eliminate — just relocated from "silently wrong number" to "silently un-fixable block." **My recommendation, for the team to weigh:** either don't let a fallback/placeholder unit (specifically `'units'` arrived at via `_unitOrDefault`'s blank-text branch) ever seed `canonicalUnit` — only a unit the parser or user actually asserted with some confidence should get to be authoritative — or have the two catch sites special-case `PantryUnitMismatchException` with a message naming the ingredient and both units, and stop batching the whole review confirm in one transaction so one bad row doesn't block the rest. I'd treat this as non-blocking on its own (it's a rarer trigger than the two open blocking findings, and it fails safe rather than corrupting data), but it's the kind of thing I'd want a deliberate yes/no on before launch rather than shipping silently.

### The `lastUsedAt` fix (R-15) — mostly right, one residual gap the new tests document but don't close

`plan_repository.dart:284-336` now only restores `previousLastUsedAt` when no *later* `cooked_adjustments` row for the same ingredient is still live (`t.id.isBiggerThanValue(adjustment.id)`), passed through to `PantryRepository.restoreFromCook`'s new `restoreLastUsedAt` flag. I traced the id-ordering assumption this rests on: `cooked_adjustments.id` is autoincrement and rows are only ever inserted by `markCooked` in real chronological cook order, and only ever deleted by `undoCooked` for the specific entry being undone — so "a later id row for this ingredient still exists" is a sound proxy for "a more recent cook is still standing." That's correct, and the primary scenario is fixed and tested: cook A, cook B, undo A while B stands — quantity restores correctly and `lastUsedAt` correctly stays at B's timestamp instead of reverting to A's stale snapshot (`test/data/plan_repository_test.dart`, first new test in the `markCooked / undoCooked` group).

The two-plan-entries-sharing-an-ingredient case is covered, but not completely closed. The second new test — "undoing the later cook after the earlier one is already undone still restores lastUsedAt" — cooks A then B, undoes A (correctly leaving `lastUsedAt` at B's time), then undoes B too, and asserts the final `lastUsedAt` is `DateTime(2026, 1, 6)` (A's cook time) rather than `null` (the ingredient's actual state before either cook — it was added fresh with no prior use). That's a real, if narrow, residual gap: undoing both cooks in oldest-first order leaves `lastUsedAt` stamped with a stale intermediate value instead of fully reversing to no-use-recorded, because B's stored `previousLastUsedAt` snapshot was captured relative to the state *when B cooked*, not relative to what's still standing by the time B is undone. (Undoing newest-first — B then A — does fully reverse to `null`, since each step's snapshot is exactly correct relative to what's already been undone by that point; I traced this by hand rather than running it, per the no-mutation-testing instruction, but the asymmetry follows directly from how `previousLastUsedAt` is captured once at cook time and never revised.) This is the same severity class as the original finding — `lastUsedAt` only feeds sort order and urgency scoring, never quantity — and the new test's own naming and comment show the team knows this is what happens; I just don't think "restores to a stale intermediate value" was the intended end state for "undo everything," and it's worth a one-line note in that test (or a follow-up ticket) rather than reading as fully resolved.
