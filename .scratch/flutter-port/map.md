# Flutter Port — Architecture & Migration Spec

## Destination

A locked architecture + migration spec for a **big-bang replacement** of the Expo/React Native app (`mobile/`) with a native **Flutter** app targeting iOS and Android. The spec also decides whether a phone-sized Flutter-web build is worth keeping as an optional **local** dev-loop convenience harness for agent-driven testing (never a CI fixture, never a shipped target) — contingent on a later speed benchmark against driving a real emulator, since Chrome can't be benchmarked against an app that doesn't exist yet. The spec resolves: the Flutter stack (routing, state management, local persistence), auth architecture, native-integration equivalents (camera, audio), component/design-system boundaries, a full per-flow UX review of current user-facing behavior (with a haptics/transitions "quick wins" pass), the iOS/Android build & release pipeline (incl. two manually-triggered CI jobs — macOS for the iOS Simulator, Linux/KVM for the Android emulator — both also runnable locally from a single Mac laptop, running one shared `integration_test` suite), and a test-migration strategy (most current Jest/RTL and Maestro coverage becomes Flutter unit/widget tests; anything that doesn't make sense post-port is identified for drop, not blindly ported). Reaching the destination means every ticket is closed and the decisions are synthesized into a written `FLUTTER_MIGRATION.md` in the repo. **Pure planning** — this map does not write Flutter app code; that's separate future execution work against whatever branch picks up the finished spec.

## Notes

- Domain: mobile app architecture / Flutter migration planning for Glean (recipe/pantry/meal-planning app). Backend (`backend/`, FastAPI on Lambda) is untouched by this effort.
- Consult `/grilling` and `/domain-modeling` for decision tickets; `/prototype` for "how should it feel" questions (haptics, transitions, UX); `/research` for external Flutter-ecosystem knowledge.
- Current stack being replaced (for reference during review): Expo Router (file-based, React Navigation v7) · TanStack Query · Drizzle ORM over `expo-sqlite` (local store for pantry/meals/plan/shopping — not just a cache) · `expo-auth-session` + `expo-secure-store` for OAuth · `expo-camera` (receipt scanning) + audio recording (`RECORD_AUDIO`, "describe" screens) · Jest/RTL unit+component tests · Maestro YAML e2e flows.
- User-facing behavior is the north star: if a UX question doesn't have an obvious answer, grill the user rather than guessing — don't resolve UX tickets by assumption.
- Test-migration tickets should actively recommend dropping tests that test implementation details or behavior that won't exist post-port — "port everything" is not the default.
- Backend API is a **frozen contract** except where a specific existing endpoint proves genuinely awkward for Flutter (narrow, ticket-by-ticket exception, not planned upfront).
- No client-side data migration/export path — local SQLite data loss on cutover is accepted (pre-launch app).
- Research tickets: write findings to `.scratch/flutter-port/research/<slug>.md`, cite primary sources, and note the branch/worktree they landed on in the ticket's resolution.
- CI topology for the cross-platform `integration_test` run is two separate `workflow_dispatch`-gated GitHub Actions jobs (macOS runner → iOS Simulator; Linux runner → Android emulator via KVM), not one combined macOS job — see ticket 17. Both must also be runnable locally on a single Mac laptop.
- The Flutter-web test harness (ticket 04's research) is **not** committed infrastructure — it's optional, local-only, and contingent on a speed benchmark deferred to early implementation. See ticket 18.

## Decisions so far

- [Research: camera/audio integration](issues/03-research-camera-audio.md) — the "describe" screens are text-input, not audio; `RECORD_AUDIO` is a vestigial permission for an unbuilt dictation feature. Recommends `camera` (not `image_picker`) for receipt scanning; `speech_to_text` (or `record` if server-side transcription instead) for future dictation; `permission_handler` for runtime permissions.
- [Research: routing/state/persistence landscape](issues/01-research-state-routing-persistence.md) — leans `go_router` (official, tab-stack fit), Riverpod (only option with TanStack-Query-like caching primitives), `drift` (best-maintained, closest to current Drizzle experience; Isar's maintenance is stalled).
- [Research: auth/secure-storage landscape](issues/02-research-auth.md) — leans `flutter_appauth` + `flutter_secure_storage` + `app_links` (not `uni_links`, discontinued). Flags: iOS Keychain survives uninstall (must clear on explicit logout), and two doc claims need direct re-verification before ticket 07.
- [Research: build pipeline + macOS CI](issues/05-research-build-release-macos-ci.md) — **real blocker**: GitHub-*hosted* macOS runners can't run the Android emulator (nested-virtualization limit, confirmed unresolved 2026, feature request closed "not planned"). Doesn't apply to a self-hosted runner on a physical Mac. Ticket 09 must first disambiguate which one "manual macOS CI job" means — that wasn't pinned down when scoped.
- [Research: Flutter web as CI test target](issues/04-research-flutter-web-test-target.md) — sound pattern (`flutter drive -d web-server` + chromedriver, phone-viewport via browser flag), but `TargetPlatform` resolves to the CI host OS (Linux), not iOS/Android — platform-adaptive gestures/theming/native-plugin behavior won't be faithfully tested on web. *(Superseded framing: this was never meant to be CI infrastructure — see [ticket 18](issues/18-decide-web-harness-worth-building.md) for the actual decision.)*
- [CI job topology for the integration_test run](issues/17-decide-ci-job-topology.md) — two separate `workflow_dispatch` jobs: macOS→iOS Simulator, Linux(KVM)→Android emulator. Both also runnable locally on one Mac laptop.
- [Whether to build the Flutter-web local harness](issues/18-decide-web-harness-worth-building.md) — deferred, not committed: only build it if an early-implementation timing check shows driving Chrome is meaningfully faster than driving a real emulator for an agent's local dev loop; otherwise skip it.
- [Flutter stack decision](issues/06-decide-stack.md) — locked: `go_router` + Riverpod (+ a thin custom query-caching layer) + `drift`.
- [Flutter auth architecture](issues/07-decide-auth.md) — locked: unchanged Cognito+Google, `flutter_appauth` + `flutter_secure_storage`, keep the custom URL scheme (universal-links migration deferred to [ticket 19](issues/19-later-migrate-to-universal-links.md)), explicit token-clear on logout, and a `--dart-define` auth-bypass flag for tests (feeds ticket 16).
- [Component & design-system architecture](issues/08-decide-component-architecture.md) — locked: Material everywhere (no Cupertino), tokens onto `ColorScheme`/`TextTheme` + one `ThemeExtension` accessed via `Theme.of(context)`, dark mode deferred but door left open, built-in `Icons` (`_rounded`) with per-glyph `flutter_svg` vendoring as the escape hatch, feature-first `lib/features/<feature>/` with extracted sub-widgets. **Deletes rather than ports**: `AppText` + its lint guard, `SwipeDeleteRow`+`swipe-action` (→`Dismissible`), `Toast`+dependency (→`SnackBar`), `expo-haptics` (→built-in `HapticFeedback`), `LayoutAnimation`. **Adds the missing `Button` primitive** — 12 of 15 route files hand-roll pill buttons today.
- [Signing & release pipeline](issues/09-decide-build-release-pipeline.md) — locked: Fastlane release lanes run from the Mac (not CI initially), `match` skipped until a second signer exists, Codemagic passed over. EAS goes away entirely (`eas.json` + `eas-build.yml` delete) — note it was silently providing signing credentials *and* remote build-number auto-increment, the latter needing an explicit replacement. All current profiles are internal-only: there has never been a public store release.
- [Haptics & transitions house rules](issues/10-quick-wins-haptics-transitions.md) — locked: a semantic three-weight ladder (`selectionClick`/`lightImpact`/`mediumImpact`) applied at the design-system level; skeleton cross-fades, animated list mutations, an animated Plan progress ring, `flutter_native_splash` to unify the two splash compositions. **Corrects ticket 08**: Flutter has no notification-style haptic, but `hapticNotify` is never called today, so dropping it is zero-regression and no package is needed.
- [Cross-cutting UX rules](issues/_cross-cutting.md) — locked: swipe-only deletes (`Dismissible`) with an **undo snackbar** on every destructive action incl. "Cooked"; **all user-data tables scoped to the user** (fixes cross-account leakage, free now that no data migrates); a short skippable **first-run setup**.
- [UX review: Pantry](issues/11-ux-review-pantry.md) — expiry **inferred** from category (settable deferred); all three intake modes behind a `+` sheet (fixing `add.tsx`/`manual-entry.tsx` being unreachable dead code); intake becomes a **modal task** with the tab bar hidden (today a mid-scan tab tap silently loses the capture); the twin review screens **unify into one**; fake 3-step progress replaced with an honest indicator (removing ~2.3s of artificial delay); quantity editing moves to a sheet covering quantity + unit + expiry.
- [UX review: Meals](issues/12-ux-review-meals.md) — the library becomes **deliberately curated**: tap previews rather than saves, the dead bookmark icon becomes the real save/unsave toggle, and recipes become deletable (no `deleteRecipe` exists today). **Allergens (`not_suitable_for`) and `source_url` attribution get surfaced** — both stored and displayed nowhere.
- [UX review: Shop](issues/13-ux-review-shop.md) — **checkout stops deleting unmatched items** (today scanning a receipt matching 4 of 12 checked rows loses the other 8); explicit "Done shopping" so a receipt-less trip can complete; **manual items resolve to an ingredient identity on entry**, fixing the root cause of them never matching a receipt.
- [UX review: Plan](issues/14-ux-review-plan.md) — the plan becomes **week-scoped with week pagination** (today "This Week" has no date filter and lifetime-count capacity eventually locks out all adds); cooked meals stay visible but don't count toward "left to plan"; **uncooked meals roll forward**; generation stays top-up only.
- [UX review: Settings & auth](issues/15-ux-review-settings-auth.md) — Settings **auto-saves** (removing the dirty-state trap where live stats made unsaved state look saved); on token expiry local data **stays readable** behind a signed-out banner gating AI features; the auth bypass moves to a separate `main_e2e.dart` entrypoint that cannot compile into a production binary.
- [Ingredient categorisation](issues/22-decide-ingredient-categorisation.md) — **the one sanctioned backend change**: parse endpoints return `category`/`food_group`. Nothing assigns a category today, which broke three features at once — pantry grouping collapsed to "Other", meal-plan generation 422'd on uncategorised items, and expiry inference had no basis.
- [Test-migration strategy](issues/16-test-migration-strategy.md) — locked: 50 Jest files → 28 unit / 14 widget / 1 integration / **7 dropped**; 11 Maestro files → `smoke.yaml` becomes the single `integration_test` suite, 3 fold into widget tests, **5 helpers dropped**. Biggest leverage: **no test currently touches a real database** — one in-memory `drift` fixture replaces five copy-pasted mock harnesses and turns call-shape assertions into outcome assertions. Ten areas of **new** coverage identified, incl. non-negotiable tests for the checkout data-loss fix and user-scoped data isolation.
- [Data-layer architecture](issues/20-decide-data-layer-architecture.md) — locked: the backend holds **no user state** (stateless processors + read-only recipe corpus), so no repository/sync layer. Local drift `.watch()` → `StreamProvider` is the source of truth (the manual `useFocusEffect`→`load()`→refetch dance deletes itself); remote API becomes command providers returning ephemeral proposals committed into drift. Screens never touch drift/API directly. Corrects ticket 06's "custom query-caching layer" as unnecessary.

## Not yet specified

- App Store / Play Store release process details (store listings, screenshots, review-guideline gotchas) — too early to ticket until the build/release pipeline decision (ticket 09) lands.
- Anything the per-flow UX reviews (tickets 11–15) surface that changes current behavior materially enough to need its own follow-up decision (e.g. a flow redesign) — will graduate into fresh tickets as those close.
- Exact scope of what `FLUTTER_MIGRATION.md` needs as a final section list — will sharpen once most decision tickets are closed and there's real content to structure.

## Out of scope

- **Coexistence / staged rollout** of the RN and Flutter apps side by side — ruled out in favor of big-bang replacement.
- **Client-side data migration/export** from the old app's local SQLite store — data loss on cutover is accepted.
- **Backend/API changes** — frozen contract, except a narrow case-by-case exception for an endpoint shape that proves genuinely awkward for Flutter.
- **Writing the Flutter app itself** — this map produces the spec only; implementation is separate future work.
- **Day-mapped meal slots** (assigning each planned meal to a specific weekday, enabling "what's for dinner tonight" and reminders) — ruled beyond this effort in ticket 14; it forces decisions about skipped days and drag-reordering that belong to a feature effort, not a port.
- **Nutrition display** — stored but unshown; needs design work and the data shape may be inconsistent across sources (ticket 12).
- **Dark mode** — deferred in ticket 08; the context-based token access pattern keeps it cheap to add later.
